# 数据入库：换数据库 & 导入不同格式

本文分别说明数据库迁移和多格式数据导入。

---

## 一、数据库文件类型能改吗

### 现状

`sentinel.db` 是一个 **SQLite 单文件**。它不是"格式可以改"的文件，就是 SQLite 的二进制格式。
你不能把它改名成 `.mysql` 或 `.sql`，也不能用 Excel 直接打开编辑（会损坏）。

但它能**导出**成通用格式：

```bash
python export_data.py               # 9 张表 → exports/*.csv
python export_data.py --table judge_logs
```

导出的 CSV 可以直接丢进 Excel、Power BI，或导入 MySQL / PostgreSQL。

### 想换成 MySQL / PostgreSQL，要改什么

所有 SQL 都集中在 `db.py` 一个文件里，这是当初刻意的设计。要换库，改这四处：

| 项 | SQLite（现在） | MySQL | PostgreSQL |
|---|---|---|---|
| 驱动 | `sqlite3`（内置） | `pymysql` | `psycopg2` |
| 占位符 | `?` | `%s` | `%s` |
| 自增主键 | `INTEGER PRIMARY KEY AUTOINCREMENT` | `INT AUTO_INCREMENT PRIMARY KEY` | `SERIAL PRIMARY KEY` |
| 列检查 | `PRAGMA table_info` | `SHOW COLUMNS` | `information_schema.columns` |
| 事务 | `with conn:` | `conn.begin()` | `conn.begin()` |

**不用改的**：业务逻辑、路由、规则引擎、前端。
因为前端只调 HTTP 接口，`db.py` 对外只暴露 `judge_log()` / `list_review()` 这类函数，SQL 没有泄漏到别的文件。

工作量：约 **半天**（改驱动 + 跑一遍 9 张表的建表语句 + 验证 20 个接口）。

### 什么时候该换

| 情况 | 建议 |
|---|---|
| 单机演示、离线部署 | **SQLite 更合适**，零配置、单文件、便于分发 |
| 多人同时写（> 5 人） | 换。SQLite 写锁是整库级的，并发写会排队 |
| 需要网络访问（异地/多端） | 换。SQLite 是本地文件 |
| 数据量 > 百万行 + 复杂查询 | 换。SQLite 缺少并行查询和索引优化器 |
| 要做权限分级、审计日志 | 换。SQLite 没有用户体系 |

**选型说明**：当前版本用于验证产品链路，不是生产部署。所有 SQL 收敛在 `db.py`，迁移到 MySQL/PostgreSQL 的成本相对可控；原型阶段优先保证部署简单、可复现和便于分发。

## 二、批量导入新规则 / 新知识

### 支持的格式

| 格式 | 规则（结构化） | 条款（文本） | 说明 |
|---|:--:|:--:|---|
| `.csv` | ✅ | ✅ | 有 `type` 列按规则处理，否则按文本 |
| `.json` / `.jsonl` | ✅ | ✅ | 数组或 `{"rules":[...]}` |
| `.xlsx` | ✅ | ✅ | 首行是表头则按规则，否则每行一条文本 |
| `.docx` | — | ✅ | 段落 + 表格内容都会读 |
| `.md` / `.txt` | — | ✅ | 按标题或空行切块 |
| `.pdf` | ❌ | ❌ | 需先转成 docx/txt（不做 OCR，避免解析质量不可控） |

### 用法

```bash
# 只解析 + 校验，写到暂存区（不动生产库）
python import_library.py samples

# 校验通过后并入 rules.jsonl
python import_library.py samples --commit
python check_catalog.py        # 并入后必须跑一致性检查
```

### 处理流程

```
文件 → 解析 → 逐条校验 → 归一化去重 → 暂存区 → 人工确认 → 生产库
```

**四道关口：**

| 关口 | 检查什么 |
|---|---|
| 校验 | 必填 `id/type/severity/patterns`；`severity` ∈ high/mid/low/none；**引用的条款必须存在** |
| 去重 | 归一化后比对（全半角统一、去标点空格、转小写），与生产库 + 暂存区都比 |
| 暂存 | 规则写 `rules_staging.jsonl`，条款写 `clauses_imported.jsonl`，状态 `open` |
| 人工 | 条款进审核管理页确认；规则必须 `--commit` 才并入 |

### 实际跑出来的报告

```
条款导入示例.docx    0 条规则 · 4 条文本
条款导入示例.md      0 条规则 · 4 条文本
规则导入示例.csv     3 条规则 · 0 条文本
规则导入示例.jsonl   1 条规则 · 0 条文本
规则导入示例.xlsx    2 条规则 · 0 条文本

规则：通过 6 条 · 拒绝 1 条
  ✗ 规则导入示例.jsonl [R17] 缺 type；severity 非法：'超严重'（应 high/mid/low/none）；
                            缺触发词；依据条款不存在：NOT_EXIST
条款：新增 8 条 · 重复跳过 4 条
```

**注意那 8 条条款都写着"需人工确认后才会生效"**——导入不等于启用。

### 为什么不让导入直接生效

三个理由：

1. **新规则会立刻影响线上判定**，一条写错的规则可能把正常对话判成违规
2. **条款引用必须是真实存在的**，否则提醒卡上会显示一个查不到的依据编号
3. **同一句话有 20 种写法**，重复规则会让优先级打架

所以：**导入是"提货"，不是"上架"**。上架必须走人工确认。

### 去重是怎么做的

```python
norm("您好，好评返现5元") → "您好好评返现5元" → sha1 → "a3f2..."
```

全半角统一、标点空白全去掉、转小写。
所以「好评返现５元」和「好评返现5元！！」会被认成同一条。

## 三、一批真实资料该怎么走

假设拿到一份 60 页的《平台交易规则》PDF：

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 | PDF → docx（用 Word 或 LibreOffice 转） | `平台规则.docx` |
| 2 | `python import_library.py 平台规则.docx` | `clauses_imported.jsonl`（N 条 open） |
| 3 | 打开审核管理页，逐条确认/合并 | 通过的条款 |
| 4 | 按条款写规则（或从候选池生成草稿） | `rules_staging.jsonl` |
| 5 | `--commit` + `check_catalog.py` | 生效 |

**第 3 步是瓶颈也是价值所在**——60 页文档切出来的条款，大概只有 1/3 值得做成规则。
这个判断没法自动化，但它正是这个岗位的活。

## 四、已知限制（不藏着）

| 限制 | 影响 | 缓解 |
|---|---|---|
| PDF 不支持 | 需手动转格式 | 转换质量比自动 OCR 可控 |
| 没有版面理解 | docx 表格能读但会拍平成一行 | 复杂表格建议先整理 |
| 切块按标题/空行 | 无标题的长文档切得粗 | 先用 Word 加标题样式 |
| 不做语义去重 | "退货"和"退款"两个词视为不同规则 | 依赖人工合并 |
| 导入不自动生成规则 | 条款 → 规则仍需人工写 | 后续可加"候选规则草稿生成" |
