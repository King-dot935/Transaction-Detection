# 数据源与规则清单

> 由 `build_catalog.py` 从 `data/` 自动生成，改完数据重跑即可，不用手改文档。

## 一、四类数据源，各管一件事

| 数据源 | 文件 / 表 | 装什么 | 谁维护 | 被谁读 | **不装什么** |
|---|---|---|---|---|---|
| **规则库** | `data/rules.jsonl`（12 条） | 「商家怎么说算越界」：触发词、严重度、优先级、动作 | 产品 + 风控运营 | 判定引擎、实验台、分流器 | 不装法律条文原文，也不装用户会话 |
| **知识库** | `data/clauses.jsonl`（28 条） | 「凭什么这么说」：平台规则条款、适用范围、例外 | 法务 / 规则运营 | 提示卡、介入单 | 不装触发逻辑，也不装具体案例 |
| **标注集** | `data/scenarios.jsonl` + `holdout*.jsonl` | 「判得对不对」：人工标注的对话与期望结果 | 产品 | 评测脚本 `run_eval.py` | 不参与线上判定 |
| **运行数据** | `sentinel.db`（`judge_logs` / `review_queue` / `feedback`） | 「实际发生了什么」：每次判定、待复核、用户反馈 | 系统自动写 | 审核管理、指标页 | 不回流成规则，需人工确认 |

**职责边界**：规则库定义「像不像」，知识库说明「凭什么」，标注集验证「对不对」，运行数据记录「实际怎样」。

## 二、一条消息进来，数据是怎么被调用的

```
商家消息
  │
  ├─① 负向抑制  读 rules.jsonl 里 negative=true 的条目（R12）
  │     命中「可以退 / 已经安排」→ 直接放行，不往下走
  │
  ├─② 正向匹配  读其余 11 条规则的 patterns / rights+denials
  │     命中多条 → 按「严重度 → priority」排序取第一条
  │
  ├─③ 取依据    用命中规则的 clause 字段去 clauses.jsonl 查条款
  │     查不到 → 提示卡降级为泛化文案（现在 12 条全部能查到）
  │
  ├─④ 分流      router.decide()：规则能定就定，含糊的交小模型/大模型
  │     判定不了 → 写 review_queue 等人
  │
  ├─⑤ 落库      写 judge_logs（规则、tier、成本、原因）
  │
  └─⑥ 展示      提示卡 = 类型 + 依据条款 + 你能主张什么 + 两个动作
```

| 步骤 | 读什么 | 写什么 |
|---|---|---|
| ① 负向抑制 | `rules.jsonl` negative 条目 | — |
| ② 正向匹配 | `rules.jsonl` 正向条目 | — |
| ③ 取依据 | `clauses.jsonl` | — |
| ④ 分流 | `router.py` 内置信号表 | — |
| ⑤ 落库 | — | `judge_logs`；判不了写 `review_queue` |
| ⑥ 复核 | `review_queue` | 裁决写回 `judge_logs(source=human)` |

## 三、规则全表（12 条）

| ID | 类型 | 严重度 | 优先级 | 触发方式 | 依据条款 | 动作 | 需累计 |
|---|---|---|---:|---|---|---|---|
| R12 | 正常沟通 | none | 0 | （负向抑制）已经安排 / 今天发出 / 帮您登记 / 可以退 | — | 抑制 | 否 |
| R03 | 诱导线下交易 | high | 1 | 加微信 / 加我微信 / 加我好友 / 加v / 私聊… | TRANS_2.1（平台内完成交易） | 立即介入 | 否 |
| R04 | 以利益换好评 | high | 1 | 删差评 / 差评删 / 改好评 / 好评返现 / 删了评价… | EVAL_4.2（评价的独立性） | 立即介入 | 否 |
| R05 | 威胁或辱骂 | high | 1 | 你等着 / 投诉也没用 / 爱要不要 / 滚 / 废物… | COMMUNITY_3.4（沟通行为规范） | 立即介入 | 否 |
| R08 | 索要不必要的身份信息 | high | 1 | 身份证照片 / 手持身份证 / 银行卡号 / 验证码 / 密码… | PRIVACY_8.1（个人信息的必要范围） | 立即介入 | 否 |
| R02 | 扩大退货例外 | mid | 5 | 拆封不退 / 拆开不退 / 拆封了就不能退 / 拆开就不退 / 拆封的不能退… | RETURN_7.3（已使用商品的退货限制） | 提示权利 | 否 |
| R09 | 诱导放弃权利 | mid | 5 | 签收即认可 / 签收就代表认可 / 详情页写了 / 最终解释权 / 概不退换 | RETURN_7.1（七天无理由退货的适用范围） | 提示权利 | 否 |
| R10 | 拒绝开票 | mid | 5 | 不开发票 / 开不了发票 / 没有发票 / 不开票 | INVOICE_10.1（发票开具） | 提示权利 | 否 |
| R01 | 拒绝法定权利 | mid | 10 | 权利词（退、换、售后、发票、开票）同时出现拒绝词（不退、不能退、不支持、不给退…） | RETURN_7.1（七天无理由退货的适用范围） | 提示权利 | 否 |
| R06 | 责任推诿 | mid | 30 | 物流的问题 / 找快递去 / 你签收就代表 / 我们没责任 / 你自己弄坏… | QUALITY_9.1（质量问题退货的判定） | 提示权利 | 否 |
| R07 | 反复拖延 | low | 40 | 明天回复 / 稍等 / 在处理了 / 等通知 / 再等等… | SERVICE_16.1（客服响应时效） | 提示 | 3 次 |
| R11 | 虚假承诺 | low | 50 | 假一赔十 / 保证正品 / 绝对没问题 / 百分百 | QUALITY_9.1（质量问题退货的判定） | 提示 | 否 |

**读法**：先比严重度，再比 priority，**数字越小越靠前**。
同一严重度（都是 mid）时，R02（priority 5）压过 R01（priority 10）——也就是说「拆封不退」优先判成「扩大退货例外」，而不是笼统的「拒绝法定权利」。

## 五、一致性自检

跑 `python check_catalog.py`，检查四件事：

1. 每条规则的 `clause` 都能在知识库里找到
2. 每条条款是否至少被一条规则引用（未引用会列出来，不算错）
3. 同一个触发词是否出现在多条规则里（会打架，靠优先级裁决，但要看得见）
4. 高危规则是否都挂了依据

## 六、几条硬约定

- **规则不写文案**：提示语里的「你能主张什么」来自条款的 `text`，不另写一份，避免两边不一致
- **条款不写触发词**：条款只描述规则，不描述怎么说；话术识别全部留在规则库
- **运行数据不自动改规则**：人工裁决先落库当标注，改规则必须人工过一遍
- **不存用户隐私原文进知识库**：知识库只有平台条款，会话原文只在运行数据里，且有留存期
