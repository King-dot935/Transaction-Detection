# 和真实电商聊天介入的差距

先给结论：**这个 demo 是"离线质检器"，真实系统是"在线拦截器"。**
差距不在判定算法，在**接入方式、会话建模、处置闭环**这三件事上。

---

## 一、差距清单

| # | 维度 | 真实电商 | 这个 demo | 能对齐吗 |
|---|---|---|---|---|
| 1 | 判定单位 | **会话**（多轮、有状态） | 单句为主 | ✅ 已补（`session.py`） |
| 2 | 触发时机 | **发送前拦截**（毫秒级） | 事后 HTTP 判定 | ✅ 已补（`/api/check`） |
| 3 | 流式接入 | WebSocket / 长连接推送 | 一问一答 HTTP | ⚠️ 部分（可加 SSE） |
| 4 | 指代消解 | 完整上下文建模 | 规则补全（"这个"→上一轮实体） | ⚠️ 部分 |
| 5 | 累计频次 | 会话内累计 | ✅ 已补（阈值规则会话聚合） | ✅ |
| 6 | 处置动作 | **真拦截消息 / 强制改写 / 工单** | 只给建议 + 转人工 | ❌ 需 IM 系统权限 |
| 7 | 双端提示 | 商家端（改写建议）+ 消费者端（维权提示） | 只有消费者端 | ❌ 需双端接入 |
| 8 | 订单/物流上下文 | 判定时带订单、物流、历史纠纷 | 只有一句文本 | ⚠️ 可加（orders 表已有） |
| 9 | 实时优先级 | 高风险先判、低风险异步 | 全部同步 | ⚠️ 可加 |
| 10 | 模型灰度 | AB 实验、按比例放量 | 无 | ❌ 需流量分桶 |
| 11 | 数据回流 | 人工标注 → 训练模型 | 只有规则候选池 | ❌ 无训练链路 |
| 12 | 多租户/权限 | 按商家隔离、按角色授权 | 无 | ❌ 需鉴权体系 |
| 13 | 性能 | 万级 QPS | 单机 HTTP | ❌ 需工程化 |

**结论**：1/2/5 已经对齐，3/4/8/9 可以继续做，6/7/10/11/12/13 不是这个产品能单方面解决的——
它们依赖 IM 权限、训练平台、鉴权体系、分布式部署。

## 二、已做的三项对齐

### 1. 会话级判定（`session.py`）

真实场景里，**单句往往判不出来**。三类情况：

| 场景 | 单句判定 | 会话判定 |
|---|---|---|
| 反复拖延 | 每句都不算违规 | 累计 3 次 → 成立 |
| 指代 | "这个不能退" 不知道指什么 | 补全成"电饭煲不能退" |
| 组合 | 承诺退货 + 加条件，单看都正常 | 合并后是"以利益换好评" |

实测（反复拖延，阈值 3）：

```
第1轮 命中['反复拖延'] 累计{'反复拖延': 1} → allow
第2轮 命中['反复拖延'] 累计{'反复拖延': 2} → allow
第3轮 命中['反复拖延'] 累计{'反复拖延': 3} → warn
    动作：提示商家并记录 · 会话内「反复拖延」累计 3 次（阈值 3）
```

对外三个接口：

```
POST /api/session/judge   {session_id, role, text}  一轮会话判定
GET  /api/session/<id>                              查会话结论
POST /api/check           {text, session_id?}       发送前快检
```

会话状态落库（`sessions` 表）：轮数、各类型累计、会话结论、原因。

### 2. 发送前拦截（`/api/check`）

这是真实产品的**主战场**——消息发出去之前就拦，而不是事后质检。

| 特性 | 实现 |
|---|---|
| 只走规则 | 不调模型，目标 <50ms |
| 带会话上下文 | 复用了指代补全 |
| 带归一化 | "身份证拍" 和 "拍身份证" 都能命中 |
| 返回三态 | `block` / `allow`（+ 命中类型与关键词） |

实测：

```
加我微信，转账给你   → block  0ms  ['诱导线下交易']
你把身份证拍给我     → block  0ms  ['索要不必要的身份信息']
好的，48小时内发货   → allow  0ms  []
```

### 3. 指代补全

```python
"电饭煲不支持七天无理由退货"  →  "这个不能退"
补全为：电饭煲不能退 | 用了上下文: True
命中：['拒绝法定权利']
```

**这不是真正的指代消解**，是最朴素的替换：把"这个/那个/它"换成上一轮的主语。
覆盖高频说法，长尾靠模型。但先有这一层，比没有强得多。

## 四、不能单方面对齐的（说清原因）

| # | 缺什么 | 为什么 demo 做不到 |
|---|---|---|
| 6 | 真拦截消息 | 要有 IM 系统写权限。demo 只能在旁边给建议 |
| 7 | 商家端改写建议 | 要有商家端 SDK / 插件 |
| 10 | 模型 AB 灰度 | 要有流量分桶和实验平台 |
| 11 | 数据回流训练 | 30 条标注不够训练，且没有训练基础设施 |
| 12 | 多租户鉴权 | 需要账号体系（当前连登录都没有） |
| 13 | 万级 QPS | 单机 SQLite + 单进程 HTTP |

**这些缺口主要来自接入权限、组织流程和基础设施，而非方案遗漏。** 当前原型只能覆盖已获得数据和系统权限的部分。

## 五、如果只能再改一件事

选 **处置闭环**，不是判定精度。

现在判定完只有"建议 + 转人工"，用户不知道结果，商家不知道代价。
真实系统里，拦截是有后果的：

```
命中 → 消息发不出去 → 商家改写 → 才能发出
```

**没有后果的判定，等于没有判定。**

最小可行的对齐：拦截后生成一条「待处理工单」，带 SLA（如 2 小时），
商家端能看到、消费者端能查到进度。这条链路一旦通了，
前面所有判定才有意义。

## 六、一句话总结

> **这个 demo 已经能"判"，但还不能"管"。**
> 判是算法问题，管是系统问题——而真实电商介入的价值，八成在"管"上。
