# 各类文件是怎么解析的

这份文档讲 `import_library.py` 的内部做法：**每种格式用什么库、切成什么、哪些会丢、哪些会错**。

---

## 一、总体思路：先归一，再判断

不针对每种格式写一套入库逻辑，而是**先转成统一中间表示（IR）**，后面所有校验/去重/入库只认 IR。

```
.csv  ─┐
.xlsx ─┤
.json ─┼─▶ 抽取器 ─▶ IR ─▶ 校验 ─▶ 归一化去重 ─▶ 暂存 ─▶ 人工 ─▶ 生产库
.docx ─┤              │
.md   ─┘              └─ 两种形态：
.txt                     {"kind":"rule",  ...字段}     结构化规则
                         {"kind":"text",  "..."}      待切分的条款文本
```

**为什么要 IR**：加一种新格式，只写一个 `extract` 分支（约 10 行），校验、去重、报告全都不用改。

---

## 二、怎么判断「这是规则文件还是文本文件」

不靠扩展名猜，靠**看内容有没有 `type` 字段**：

| 格式 | 判断方式 |
|---|---|
| CSV | 表头行有没有 `type` 或 `类型` 列 |
| XLSX | 首行是否含 `type` / `类型` |
| JSON | 首个对象是否含 `type` 键 |
| JSONL | 第一行对象是否含 `type` 键 |

有 → 按**规则**处理（校验字段、比对条款）；没有 → 按**文本**处理（切块成条款候选）。

> 为什么这么做：同一个人可能用 CSV 存规则表，也可能用 CSV 存条款清单。
> 看内容比看后缀可靠。**但这条也有代价**，见第六节"判断失手"。

## 三、逐格式的做法

### 1. CSV

**用什么**：标准库 `csv.DictReader`

**怎么读**：先按编码回退（见第四节）拿到文本，再 `text.splitlines()` 交给 DictReader。
不用 `open()` 直接读，是为了绕开编码问题。

**得到什么**：每行一个 dict，键是表头。

**会丢什么**：
- 单元格里的换行（CSV 用引号包裹时可以保留，但 DictReader 读出来是带 `\n` 的字符串，后续切词会当分隔符）
- 数字精度（一律当字符串，`priority` 后面才 `int()`）

**常见坑**：
| 现象 | 原因 | 处理 |
|---|---|---|
| 中文变乱码 | Excel 导出默认 GBK | 编码回退自动处理 |
| 第一列表头带 `\ufeff` | UTF-8 BOM | 用 `utf-8-sig` 解码 |
| 多了一列 `Unnamed: 0` | pandas 导出的索引列 | 校验时忽略未知列 |

---

### 2. XLSX

**用什么**：`openpyxl`，`load_workbook(read_only=True, data_only=True)`

**两个参数的含义**：
- `read_only=True`：流式读，不把整个工作簿载入内存（大文件必需）
- `data_only=True`：读**计算后的值**而不是公式。否则单元格里拿到的是 `=A1&"好评返现"` 这种字符串

**怎么读**：只读活动工作表，`iter_rows(values_only=True)` 逐行取出，`None` 转空串。

**会丢什么**：
- **合并单元格**：read_only 模式下，合并区域只有左上角有值，其余是 `None`。
  → 表头如果合并过，第二行开始会读到空列名。
- 单元格样式、批注、超链接（只取值）
- 多工作表：只读第一个。多 sheet 需要拆成多个文件，或改代码遍历 `wb.worksheets`

**为什么不用 pandas**：这个项目坚持零重依赖，`openpyxl` 已经够用，且能精确控制合并单元格的行为。

---

### 3. JSON / JSONL

**用什么**：标准库 `json`

**JSON**：兼容三种结构
```json
[ {...}, {...} ]                    // 数组
{"rules": [ {...} ]}                // 带 rules 键
{...}                               // 单个对象
```

**JSONL**：一行一条，**逐行解析**，坏行跳过并计数：

```python
for i, line in enumerate(lines, 1):
    try: out.append(json.loads(line))
    except JSONDecodeError as e: bad.append((i, e))
```

**为什么行级容错**：手工维护的 jsonl 经常有一行漏了逗号或引号。
整文件失败会让人误以为"整个文件都不行"，行级容错能保住其余 99 条。

**会丢什么**：多余的键（只取白名单字段）。

---

### 4. DOCX

**用什么**：`python-docx`

**怎么读**：两处都读
1. `doc.paragraphs` → 每个非空段落一行
2. `doc.tables` → 每行拼成 `"单元格1 | 单元格2 | ..."`

**为什么表格要拍平成一行**：条款表通常是「条款名 | 内容 | 依据」三列，
拍平后变成 `"七天无理由 | 定制类除外 | RETURN_7.1"`，虽然结构丢了，但**信息全在**，人工确认时能看懂。

**会丢什么**：
| 内容 | 是否读到 |
|---|---|
| 正文段落 | ✅ |
| 表格文字 | ✅（拍平） |
| 页眉页脚 | ❌ |
| 文本框 / 艺术字 | ❌ |
| 批注 / 修订痕迹 | ❌ |
| 编号列表的序号 | ❌（只读到文字） |
| 图片 | ❌（不做 OCR） |

**注意**：修订模式下的文档，`python-docx` 读到的是**已接受修订后**的文本，还是原始文本取决于文档保存状态。遇到过就先用 Word「接受所有修订」再导。

---

### 5. Markdown / TXT

**用什么**：正则 + 手写状态机（不引第三方 Markdown 解析器）

**切块规则**：
1. 遇到 `^#{1,4}\s` 标题 → 开新块，标题文字进块首
2. 遇到空行 → 结束当前块
3. **代码块内（` ``` `）不切分**，整段保留

**为什么保护代码块**：规则文档里常带示例代码或话术模板：

````markdown
```text
可以退，你先把差评删了
```
````

如果按空行切，这段会被切成几个碎片，变成无意义的候选条款。

**会丢什么**：
- 列表层级（`-` `1.` 的缩进全丢，只留文字）
- 表格（Markdown 表格会被当成普通行）
- 链接地址（只留链接文字）

---

### 6. PDF

**不支持，也不打算支持。**

原因：

| 问题 | 说明 |
|---|---|
| 版式丢失 | PDF 里没有"段落"概念，只有坐标定位的文字，粘一起会串行 |
| 表格错乱 | 多列文字会被读成一行，且顺序不可控 |
| 扫描件需 OCR | OCR 错误率在条款这种精确文本上不可接受 |
| 页眉页脚混入 | 每页重复的页眉会污染正文 |

**替代方案**：PDF → docx（Word 或 LibreOffice 转换），再导入。
转换质量比自动 OCR 可控得多，且转换后能人工过一眼。

## 四、编码处理：为什么必须先解码再解析

中文环境的文件编码至少有四种，**猜错就是满屏乱码**：

| 编码 | 来源 | 特征 |
|---|---|---|
| `utf-8-sig` | 现代工具、Excel 另存为 CSV UTF-8 | 开头有 `\ufeff` |
| `gbk` / `gb18030` | Windows Excel 直接另存 CSV | 中文双字节，无 BOM |
| `utf-16` | 某些系统导出 | 开头有 `\xff\xfe` |
| `latin-1` | 兜底，任何字节都能解码 | 不会抛错，但可能乱码 |

**做法**：按顺序尝试，返回第一个能成功解码的：

```python
ENCODINGS = ("utf-8-sig", "gbk", "utf-16", "latin-1")
```

**为什么不先检测再用**：编码检测（chardet 那类）需要额外依赖，且对短文本不可靠。
**顺序尝试更简单、更可预测**——utf-8 解不开再试 gbk，几乎覆盖所有中文文件。

**代价**：latin-1 永远不会失败，所以"解码成功"不代表"内容正确"。
如果文件真的是 latin-1 编码的西文，会被正确读出；如果是二进制文件误当文本，会得到乱码字符串而不是报错。

## 五、校验：什么会被拒

| 检查项 | 规则 | 拒因示例 |
|---|---|---|
| `id` | 必填、唯一（含暂存区） | `缺 id` / `id 重复：R13` |
| `type` | 必填 | `缺 type` |
| `severity` | 必须 ∈ `high/mid/low/none` | `severity 非法：'超严重'` |
| `patterns` | 至少一个触发词，支持 `\|,，;；` 分隔 | `缺触发词` |
| `clause` | 必须在 `clauses.jsonl` 里存在 | `依据条款不存在：NOT_EXIST` |
| 重复 | 归一化后触发词集合比对（生产库 + 暂存区） | `与已有规则触发词完全重复` |

**一条数据可以同时报多个错**，一次列全，不用反复试。

## 六、已知会出错的情况

### 1. 判断失手：内容里恰好有 `type` 列

一份**条款清单**如果表头写成 `type,内容`，会被误判成规则文件，然后因为缺 `severity` 全部被拒。

**缓解**：看报告的"0 条规则 · N 条文本"还是"N 条规则 · 0 条文本"，不对就改表头。

### 2. 切块过粗

没有标题的纯文本，整段会被当成**一个**超长条款。
**缓解**：导入前在 Word 里给每节加标题样式。

### 3. 语义重复识别不了

「好评返现」和「五星返钱」是同一件事，但词面完全不同，去重抓不到。
**缓解**：靠人工合并；后续可加「触发词相似度」提示。

### 4. DOCX 表格列错位

表格里如果有合并单元格，`python-docx` 会把同一个单元格重复返回，
拍平后变成 `"内容 | 内容 | 内容"`。
**缓解**：导前把合并单元格拆开。

### 5. 大文件内存

XLSX 用 `read_only` 是流式的，但 DOCX 是**全量载入**。
10 万字以上的 docx 会明显卡顿。**缓解**：拆分文件。

## 七、想加一种新格式怎么办

三步，约 15 行：

```python
# 1. 在 extract_units 加分支
if ext == ".html":
    from html.parser import HTMLParser
    ...
    return [("text", block) for block in blocks]

# 2. 在文件筛选里加后缀
STRUCTURED_EXT = {..., ".html"}
TEXT_EXT = {..., ".html"}

# 3. 按需决定它进 rule 还是 text
```

**不要改**校验、去重、暂存、报告——那是 IR 之后的事，所有格式共用。

## 一句话总结

> **格式只影响"怎么读成文本/字段"，不影响"怎么入库"。**
> 复杂度和风险都在"读"这一层，所以这一层要**宽进**（多编码、多结构、坏行跳过），
> 而"入库"这一层要**严出**（必填校验、条款存在性、去重）。
