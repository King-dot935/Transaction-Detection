# 检索优化：方向、能不能做、怎么做的

当前检索是**字 bigram + Dice 打分 + SimHash 分桶**，缓存条数一多就露两个问题：

1. 分桶没撞上时要退回"最近 N 条扫描"，**O(N)**
2. 打分只看 Dice，**长句被短句压、常见 bigram 权重过大**

下面分三块：能优化哪些方向、现在能落地多少、以及已经实现的代码。

---

## 一、六个优化方向

| 方向 | 解决什么 | 现在能做吗 |
|---|---|---|
| ① 归一化 | 同一意图的不同说法 | ✅ 已做（`textnorm.py`） |
| ② 倒排索引 | 候选召回从 O(N) 降到 O(候选) | ✅ **本轮已做** |
| ③ BM25 打分 | 罕见词权重高、长文档不被压 | ✅ **本轮已做** |
| ④ 多路召回 + RRF 融合 | 字面召回 + 语义召回互补 | ✅ 融合框架已做，语义那路待接 |
| ⑤ 向量检索 | 「好评返现」≈「五星返钱」 | ⚠️ 需要 embedding 依赖 |
| ⑥ 重排（rerank） | Top-K 精度 | ⚠️ 需要小模型 |
| ⑦ 热层缓存 | 高频句走 O(1) | ✅ 精确 key 已是 O(1) |

---

## 二、现在能实现多少

### 零依赖就能做（已实现）

| 能力 | 实现位置 | 效果 |
|---|---|---|
| 倒排索引（bigram → 文档） | `retrieval.Index` | 候选召回不再全表扫 |
| BM25 打分 | `retrieval.Index.search` | 罕见词权重高，长度归一 |
| RRF 多路融合 | `retrieval.rrf` | 两路召回结果可合并 |
| 精确 key（O(1)） | `recall.key_of` | 同一句直接命中 |

### 需要加依赖

| 能力 | 依赖 | 代价 |
|---|---|---|
| 向量检索 | `sentence-transformers` / 云 embedding API + FAISS | 每查一次多 5–20ms，一个向量库 |
| 重排 | 小模型（qwen-plus 即可） | 每次多 300–800ms，但只对 Top-5 做 |
| 分面检索 | 无（自建） | 需要给每条数据打品类/场景标签 |

## 三、已实现的：倒排 + BM25

### 数据结构

```sql
rt_docs(doc_id, text, dl)        -- dl = 该文档的 bigram 总数（长度归一）
rt_post(tok, doc_id, tf)         -- 倒排表：token → 文档 → 词频
CREATE INDEX idx_rt_tok ON rt_post(tok);
```

一个 1200 条的语料，倒排表约 1.7 万行，**建索引 0.07 秒**。

### 打分公式

```
idf(t) = ln(1 + (N - df + 0.5) / (df + 0.5))
score  = Σ idf(t) · tf·(k1+1) / (tf + k1·(1 - b + b·dl/avgdl))
```

参数 `k1=1.5, b=0.75`，是 BM25 的常用默认值。

**两个设计选择：**

**① 只取 df 最小的 6 个 token**

```python
scored_toks = sorted(tf, key=lambda t: self.df(t))
use = scored_toks[:6]
```

`的、了、是` 这类 bigram 出现在每条文档里，df 接近 N，idf 接近 0，
参与计算只会拖慢速度。按 df 升序取前 6 个，既保留区分度又控制候选规模。

**② JOIN 一次取回 tf 和 dl**

```sql
SELECT p.doc_id, p.tf, d.dl FROM rt_post p
JOIN rt_docs d ON d.doc_id=p.doc_id WHERE p.tok=? LIMIT ?
```

第一版写成"先查 postings，再逐行查 dl"，2000 条语料时单次查询直接卡死
——这是典型的 **N+1 查询**，加 JOIN 后从秒级降到毫秒级。

### 实测（2000 条语料，10 条查询）

| 方式 | 单次耗时 |
|---|---:|
| 暴力 Dice 扫描 | **37.14 ms** |
| 倒排 + BM25 | **1.00 ms** |
| 加速比 | **37.3×** |

**Top-1 与暴力一致：7/10。**

差的 3 条是因为 BM25 偏爱"短且含罕见词"的文档，而 Dice 偏爱"字面重合多"的文档。
这不是 bug，是两种打分的取向不同——**所以要用两路融合，而不是二选一**。

## 四、多路召回 + RRF

单路召回总有自己的偏好，融合能互补。

```python
def rrf(rankings, k=60):
    score = {}
    for lst in rankings:
        for rank, doc in enumerate(lst, 1):
            score[doc] = score.get(doc, 0.0) + 1.0 / (k + rank)
    return sorted(score.items(), key=lambda x: -x[1])
```

`1/(k+rank)` 的好处：**只看名次不看分数**，所以两路分数量纲不同也能合并
（Dice 是 0~1，BM25 是 0~∞，直接加权平均会被 BM25 吃掉）。

推荐的三路：

| 路 | 召回方式 | 擅长 |
|---|---|---|
| 精确 | 归一化 key | 同一句 |
| 字面 | 倒排 + BM25 | 措辞接近 |
| 语义 | 向量 cosine | 换了词但同义 |

前两路现在就能跑，第三路等 embedding 接上。

## 五、还没做的，以及为什么

### 1. 向量检索

**能解决**：`好评返现5元` 和 `五星返钱` 的 Dice 只有 0.50，
归一化后仍不够 —— 需要语义空间里它们本来就近。

**代价**：
- 依赖：`sentence-transformers` + FAISS，或调云 API
- 延迟：本地小模型 5–20ms/条，云 API 30–100ms
- 一致性：换模型要重建全部向量

**建议**：等字面召回命中率卡在 60% 上不去再上，不要提前。

### 2. 重排（rerank）

**能解决**：Top-5 里排序不准。

**代价**：每次查询多一次模型调用（300–800ms），只适合"候选少但要求准"的场景
（比如条款检索），不适合每句话都判的实时链路。

### 3. FTS5

SQLite 自带 FTS5，但**中文需要分词器**（默认 unicode61 按空格切，中文整段当一个词）。
可选方案：`unicode61` + 预先把文本用空格隔开每个字（bigram 化后写入）。

**没选它的原因**：自建倒排表能精确控制 token 化方式（bigram、短句补单字），
而且和 `recall.py` 的特征保持一致，不会出现"检索用一套特征、打分用另一套"的错位。

## 六、调优清单（接上真实数据后按顺序做）

| 顺序 | 动作 | 预期收益 |
|---:|---|---|
| 1 | 用真实数据重建倒排，测平均延迟 | 确认 1ms 结论在真实规模下成立 |
| 2 | 扫 `k1`（1.2/1.5/2.0）和 `b`（0.5/0.75） | BM25 参数影响 5–10% 精度 |
| 3 | 测多路融合 vs 单路 | 融合通常再涨 3–8% Top-1 |
| 4 | 加"品类/场景"过滤（分面检索） | 候选减半，精度明显提升 |
| 5 | 接 embedding 做第三路 | 同义不同词 +15~25% 召回 |

---

## 七、一句话总结

> **索引解决"找得快"，打分解决"排得准"，融合解决"谁都不全对"。**
> 现在能拿到的：倒排 + BM25，**37× 提速**，零依赖；
> 拿不到的：语义召回，需要 embedding —— 那是下一个数量级的提升，也是最贵的一步。
