# 企业级五层自检

这里的“企业级”不是功能数量，而是数据、评测、观测、安全和稳定性是否形成可验证闭环。当前项目仍是单机原型，以下自评用于识别差距，不是上线证明。

## 总体结论

| 层面 | 已做到 | 关键缺口 | 结论 |
|---|---|---|---|
| 数据 | 标签语义拆分、30 段标注、结构校验、跨集合重复检查 | 样本少、无真实业务数据、无规则负责人/生效时间 | 可用于原型，不足以估计线上效果 |
| 召回与判定 | 规则、缓存、三级分流、人工兜底 | 关键词泛化差，部分新表达不进入模型 | 方案上限明显 |
| 评测 | 四集合、切片、缺陷清单、Wilson 区间、回归门禁 | 门禁 FAIL；负例仅 8 条，其中未调参仅 2 条 | 方法论成立，数据不足 |
| 观测 | `judge_logs`、`trace_id`、七类产品事件、SLO | 没有真实客户端、支付/工单闭环和集中监控 | 链路口径成立，业务价值未验证 |
| 稳定性 | 模型/缓存熔断、预算、背压、管理 token、只读模式 | SQLite 单点、进程内状态、无自动重判队列 | 演示可保守降级，生产不足 |

## 1. 数据

已实现：

- `truth_type` 使用 `NULL` 表示未标注，`正常沟通` 表示负例，避免把手输样本算进误报率。
- `validate_data.py` 检查字段、轮次、标签类型与跨集合重复。
- 历史污染集合和当前未调参集合在报告里分开标注。
- 落库前对手机号、身份证号、银行卡号和密钥脱敏。

不足以称为企业级：

- 30 段样本是人工构造，不代表真实分布。
- 没有数据字典审批、版本审批、负责人和保留期限。
- 没有真实聊天、订单和退款回调。

## 2. 召回与判定

链路：

```text
安全检查 → 归一化 → 缓存 → 规则 → 小模型 → 大模型 → 人工
```

已实现的工程约束：

- 规则命中带条款和严重度。
- 注入文本不进模型、不进缓存。
- 模型调用受总预算、分层熔断和单探测半开约束。
- 规则与模型冲突、低置信或模型缺失时进入人工。

核心短板：

- 当前未调参召回 25%。
- 规则在追说法，缺少语义槽和上下文判断。
- 路由风险词也偏关键词化，P04“封号”甚至不会进入模型。

## 3. 评测

已实现：

- 30 段数据分四组管理。
- 召回、误报、类型、首轮位置与 2×2 计数。
- 类型、句长、条款词切片。
- 每次评测可保存历史快照并执行门禁。
- 自动检查 ID 与商家原话跨集合重复。

当前门禁：

```text
holdout3 召回 25% < 70%       FAIL
holdout3 负例 2 < 60          FAIL
holdout3 误报 0%，n=2         无法证明低于 5%
```

不能把开发集或已被调参的 holdout 加回门禁来获得 PASS。

## 4. 观测

已实现：

- 服务端每次判定产生 `trace_id`。
- 记录 tier、成本、延迟、缓存、安全风险、是否转人工。
- 提醒卡曝光、证据展开、介入点击、反馈、审核进入、人工裁决形成事件链。
- `/api/events/stats` 返回事件计数与链路转化率，曝光不足 30 条时提示样本不足。

当前不能证明：

- 提醒有没有提升退款成功率。
- 是否降低二次投诉。
- 用户是否真的拿到钱。

原因是缺少真实 IM、支付和工单系统。

## 5. 稳定性与安全

已实现：

- 请求体上限、文本上限、读写分离限流。
- 提示注入不自动放行。
- 管理写接口 token/本机边界。
- CSP 等安全响应头。
- 模型和缓存熔断、模型 HTTP 超时受预算约束。
- 人工队列背压。
- 只读部署模式。

仍需补齐：

- 企业身份与 RBAC。
- HTTPS、密钥托管、审计留存。
- 分布式限流/熔断。
- 数据库高可用、自动恢复和故障切换。
- 模型恢复后的 durable retry queue。
- 生产告警与值班流程。

## 项目定位说明

项目已经覆盖数据、判定、评测、观测和降级五层，并为每层提供代码和可复现证据。当前门禁仍为 FAIL，未调参召回为 25%，这些结果用于定位下一轮工程改造，不作为上线效果结论。

当前最准确的定位是：**工程结构完整度较高的原型，具备继续生产化的切入点，但数据、权限、基础设施和业务闭环仍未完成。**
