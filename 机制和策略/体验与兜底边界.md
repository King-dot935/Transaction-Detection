# 体验优化方向 & 兜底兜不住怎么办

两个层面分别处理：前者关注正常体验的持续优化，后者关注关键依赖故障时的保守降级。

---

# 第一部分：用户体验优化方向

## 一、按场景列（每条都有具体做法）

### A. 会话判定页（首页）

| 问题 | 现状 | 优化方向 | 优先级 |
|---|---|---|---|
| 自动播放不知道会播多久 | 只显示"第 2/4 轮" | 显示总时长（"约 40 秒播完"）+ 进度条 | 高 |
| 想细看某一句做不到 | 播完就过 | 点气泡暂停 + 高亮对应判定卡 | 高 |
| 提醒卡出现时在右侧，视线要横跳 | 左侧对话、右侧卡片 | 卡片出现时左侧对话**自动滚到该句**并加高亮边框 | 高 |
| 判定卡信息密度高 | 三段式 + 依据 + 按钮 | 默认只显示「结论 + 一句依据」，展开看完整链路 | 中 |
| 不知道"为什么没提醒" | 有"监测中"文案 | 显示"已看 3 条，未命中规则"（已有）+ 最近一击的近似度 | 中 |
| 换场景要等 | 下拉切换 | 保持自动播放，切换时从第 1 轮开始 | 低 |

### B. 自己输入

| 问题 | 现状 | 优化方向 | 优先级 |
|---|---|---|---|
| 点「判定」后没有等待感 | 无 loading | 按钮转圈 + 输入框禁用 + 骨架屏占位卡片 | 高 |
| 判得慢时不知道在干什么 | 无进度 | 显示"规则→模型"两段式进度（"正在调小模型…"） | 中 |
| 判完不知道能干什么 | 只有"去审核管理" | 加"复制判定依据""再试一句" | 中 |
| 输入历史没了 | 每次清空 | 保留最近 5 条（本地存储） | 低 |
| 移动端键盘遮挡 | 输入栏吸底 | 已做吸底；再加 `scrollIntoView` 保证可见 | 中 |

### C. 审核管理

| 问题 | 现状 | 优化方向 | 优先级 |
|---|---|---|---|
| 一条条裁决太慢 | 单条提交 | **批量裁决**：多选 + 一次提交（同类样本） | 高 |
| 重复劳动 | 每次都要填理由 | 理由**记忆**：同类型上次用的理由一键填入 | 高 |
| 判错了没法改 | 提交即定案 | 10 秒内「撤销」+ 记录 `reverted` 状态 | 高 |
| 不知道优先处理哪条 | 按时间倒序 | 按「风险等级 × 等待时长」排序 | 中 |
| 键盘用户效率低 | 全鼠标 | 快捷键：`1/2/3/4` 选处置、`Enter` 提交、`J/K` 上一条下一条 | 中 |
| 长列表找不到 | 无筛选 | 按类型/危险度筛选 + 搜索 | 中 |

### D. 通用

| 项 | 做法 |
|---|---|
| 空状态 | 每个空列表都给"下一步做什么"，而不是"暂无数据" |
| 错误态 | 区分"网络问题/服务降级/限流"三种，分别给不同文案和重试建议 |
| 加载态 | 超过 300ms 才显示 loading（避免闪烁） |
| 可访问性 | 对比度 ≥ 4.5:1、`prefers-reduced-motion`（已做）、键盘可达 |
| 文案 | 把"引擎/链路/分流层"这类词换成"怎么判的/走哪一步" |
| 信任 | 每条结论都能点开看「依据条款 + 命中的原话」——已做，但要更容易发现 |

## 二、一条判据：用户的三次犹豫

用户在这个产品里会犹豫三次，每次犹豫都是一个优化点：

| 犹豫 | 用户心里想的 | 该给什么 |
|---|---|---|
| ① 真的被侵犯了吗 | "他说这话算违规吗" | 明确结论 + 条款依据 |
| ② 我该做什么 | "我该点哪个按钮" | 一个主行动（申请平台介入），不要三个平级按钮 |
| ③ 平台会管吗 | "点了有用吗" | 处理时效 + 可追踪的介入单号 |

**现在的实现解决了 ①，②③ 还弱**——没有时效承诺，没有介入单的查询入口。

# 第二部分：兜底兜不住怎么办

## 一、先承认：兜底本身也会坏

现在的兜底链是：

```
缓存 → 规则 → 小模型 → 大模型 → 人工
```

这条链的每一环都可能同时失效：
- 模型全挂（已做熔断）
- **人工队列也满了**（这才是真正兜不住的地方）
- 数据库挂了（连"挂起"都存不下）
- 代码 bug 导致 500（兜底代码本身有 bug）

**兜底的终极问题**：兜底需要资源，而资源在故障时恰恰最紧张。

## 二、五级防线（逐级减载，不是逐级加码）

| 级别 | 手段 | 触发 | 用户感受 |
|---|---|---|---|
| L1 | 缓存命中 | 常见 | 秒回 |
| L2 | 规则判定 | 命中规则 | 秒回 |
| L3 | 模型判定 | 规则不确定 | 0.3–5 秒 |
| L4 | 挂人工复核 | 模型也不确定 | 分钟到小时 |
| **L5 背压** | **减少受理** | **人工队列积压** | **明确告知延迟或暂停** |
| **L6 业务兜底** | 先赔付/冻结交易/人工工单 | 判定不可用 | 人工兜底处理 |

**L5 是这次新加的**——因为前面几级都失效时，继续接新单只会让队列更长。

## 三、L5 背压：已实现

```python
SOFT = 60    # 积压 ≥ 60 → throttle
HARD = 150   # 积压 ≥ 150 → shed
```

| 级别 | 行为 | 用户看到 |
|---|---|---|
| `normal` | 正常受理 | — |
| `throttle` | 不确定的一律挂起，规则能定的照常 | "当前复核量较大，预计延迟 N 小时" |
| `shed` | 直接拒绝新判定 | "系统繁忙，请 5 分钟后再试" |

实测（阈值临时调低到 1/3）：

```
积压 31 → 级别 shed
  所有请求：skipped=shed，不产生新的人工单
  提示：当前咨询量过大，系统已暂停新判定。请 5 分钟后再试

阈值改为 throttle：
  级别 throttle
  提示：当前复核量较大，拿不准的样本会转人工，预计处理延迟 4 小时
  规则能定案的仍正常判（拒绝法定权利）
```

**关键设计**：
- `shed` 时**不写新的人工单**——否则越减载队列越长
- `throttle` 时**规则能定的照常**——只有不确定的才降级，别把确定的事也拖慢
- 提示里给**预计延迟**，而不是"请稍候"

查当前级别：

```bash
curl http://127.0.0.1:8765/api/system/status
# {"pending_review": 31, "backpressure": "normal", ...}
```

## 四、再往下兜不住：L6 业务兜底

技术兜底全失效时，靠**业务规则**兜——这是产品设计问题，不是工程问题。

| 场景 | 兜底做法 | 代价 |
|---|---|---|
| 判定服务不可用，但用户在纠纷中 | **先冻结商家结算**，不依赖判定结论 | 误伤正常商家 |
| 无法判断是否违规 | 先给消费者退款，事后再追责 | 资金损失 |
| 系统完全不可用 | 转人工工单，承诺 24 小时回复 | 人力成本 |

**原则：宁可多赔，不可漏放。** 在消费者保护场景，误伤的代价小于漏放。

## 五、fail-open 还是 fail-closed？按风险分级

这是兜底设计里最容易做错的一步。

| 场景 | 策略 | 理由 |
|---|---|---|
| 高严重度（威胁、隐私、线下交易） | **fail-closed**：判不了就不放行 | 漏放代价 >> 误伤 |
| 低严重度（话术不当、拖延） | **fail-open**：判不了就放行 + 记录 | 误伤会打扰用户、损害信任 |
| 正常沟通（无风险信号） | fail-open | 本来就不该介入 |

**当前实现是全 fail-closed**（判不了一律转人工）——安全但代价大：
待复核率 16%，人工队列很快会满。

**改进方向**：按 `rule.severity` 决定 fail 方向，预计能把待复核率压到 8% 以下。

## 六、怎么发现"兜底失效了"

兜底失效通常是**静默**的——不报错，只是质量悄悄下降。要监控四个信号：

| 信号 | 异常阈值 | 说明 |
|---|---|---|
| `degrade_events` 频率 | > 10 次/分钟 | 依赖在持续失败 |
| 待复核积压 | > SOFT(60) | 人工接不住了 |
| 429 比例 | > 5% | 用户在被限流 |
| 5xx 比例 | > 1% | 系统本身有问题 |

**这四个指标比"服务是否存活"更有意义**——服务活着但一直在降级，等于不可用。

## 七、预案（兜不住时人做什么）

| 情况 | 谁 | 动作 |
|---|---|---|
| 模型连续失败 | 值班 | 确认是 key 还是服务方故障；切换备用 provider |
| 人工队列积压 > 150 | 值班 + 业务 | 提高 SOFT/HARD 阈值前先加人；或开只读模式 |
| 数据库异常 | 值班 | 切到只读 + 从备份恢复；期间判定暂停 |
| 代码 bug | 值班 | 回滚上一版本；保留降级开关 |
| 流量突增 10 倍 | 值班 | 限流收紧；非核心功能（如批量）先关 |

## 八、演练清单（不做演练的兜底等于没有）

| 演练 | 操作 | 预期 |
|---|---|---|
| 模型全挂 | 假 key | 熔断 → 全转人工 → 模式 degraded |
| 人工也满 | 把 SOFT 调到 1 | 立即 throttle，提示延迟 |
| 再满 | 把 HARD 调到 3 | shed，拒绝新请求，队列不再增长 |
| 数据库只读 | 文件设只读 | 报错明确，不是静默失败 |
| 服务重启 | `kill` 进程 | 熔断状态清零（可接受，但要知晓） |

---

## 九、一句话总结

> **体验优化的核心是"减少犹豫"**：给结论、给一个动作、给一个承诺。
> **兜底的尽头是"减载"**：当所有系统都接不住时，**停止接收比硬撑更负责**。
> 而兜底本身必须被监控——**静默的降级比崩溃更危险**。
