# 前端是怎么把数据写进数据库的

一句话：**前端自己不写数据库，它发一个 HTTP 请求，后端收到后执行 SQL。**
浏览器和数据库之间隔着后端这一层，这是安全上的硬要求，不是设计选择。

---

## 一、三层结构

```
浏览器（前端）                 服务器（后端）               磁盘（数据库）
─────────────              ──────────────              ─────────────
 页面 HTML/JS      HTTP        Python              SQL       sentinel.db
 点按钮      ──────────▶     demo.py      ──────────▶      SQLite 文件
             ◀──────────                  ◀──────────
              JSON 响应        db.py 执行 SQL
```

- 前端只会 `fetch()`，它不知道 SQL 长什么样
- 后端（`demo.py`）负责解析请求、校验、调 `db.py`
- `db.py` 是**唯一**碰 SQL 的地方
- SQLite 把数据写到 `sentinel.db` 这个文件

---

## 二、一条真实的写入链路

以「审核管理点确认介入」为例，分四步。

### 第 1 步：前端发请求

`static/review.html`：

```js
async function decide(id, action){
  const r = await fetch('/api/review', {
    method: 'POST',
    headers: {'Content-Type': 'application/json'},
    body: JSON.stringify({id: 8, action: 'approve', reviewer: '袁逍堃'})
  }).then(x => x.json());
  toast(r.message);
  loadQueue(); loadMetrics();      // 写完再拉一次最新数据
}
```

**只做一件事**：把「要对哪条、做什么」发给服务器。

### 第 2 步：后端路由接住

`demo.py` 的 `do_POST`：

```python
def do_POST(self):
    u = urlparse(self.path)
    raw = self.rfile.read(n)              # 读请求体
    payload = json.loads(raw.decode())    # 解析 JSON
    if u.path == "/api/review":
        ok, msg = db.decide_review(
            int(payload.get("id", 0)),
            payload.get("action", ""),
            payload.get("reviewer", "审核员"))
        return self._send(200, {"ok": ok, "message": msg})
```

这里做了三件事：**读 → 解析 → 交给 db 层**。它不写 SQL。

### 第 3 步：db 层执行 SQL

`db.py` 的 `decide_review()`，核心就这么几行：

```python
conn = connect()                      # 打开连接
with conn:                            # ← 事务：要么全成功，要么全回滚
    conn.execute(
        "UPDATE review_queue SET status=?, reviewer=?, decided_at=? WHERE id=?",
        (status, reviewer, now(), rid))

    if action == "approve":
        conn.execute("INSERT INTO cases(case_no, ts, text, ...) VALUES(?,?,?,...)",
                     (case_no, now(), row["text"], ...))
        conn.execute("INSERT INTO notifications(...) VALUES(...)")
        conn.execute("UPDATE merchants SET violations=violations+1 WHERE id='m-2001'")
```

`with conn:` 是**事务**——四条 SQL 一起成功才提交，中途出错全部撤销。
这样不会出现「介入单建了但通知没发」的脏数据。

### 第 4 步：SQLite 落盘

语句执行完，SQLite 把改动写进 `sentinel.db`。
下一次任何查询（页面刷新、DBeaver）都能读到。

## 三、实测：一次点击，数据库多了两行

**写之前**

```
judge_logs     33 行
review_queue    7 行
cases           6 行
```

**前端发一次判定**（等价于在实验台点「判定这句」）

```http
POST /api/judge  {"text": "你把那条评论撤掉，我立刻走退款"}
→ 返回 {"tier":"small", "pending_review":true, "review_id":8}
```

**写之后**

```
judge_logs     34 行     ← +1（每次判定都记一条流水）
review_queue    8 行     ← +1（判不了，挂起等人工）
cases           6 行     ← 不变（还没人裁决）
```

数据库里新增的那条：

```
id=8  status=pending
text:   你把那条评论撤掉,我立刻走退款
reason: 规则未命中且该层模型未配置，无法自动判定
```

**这两个 +1 就是「前端写库」的全部含义**——前端发了请求，后端把两条记录插进了表里。

## 四、为什么不让前端直连数据库

如果浏览器能直接连 SQLite/MySQL，意味着：

| 风险 | 后果 |
|---|---|
| 连接串写在前端代码里 | 打开 F12 就能看到账号密码，任何人可以拖库 |
| 前端拼 SQL | 能执行 `DROP TABLE`，一条命令删全部数据 |
| 没有校验 | 谁都能改别人的记录，改完没人知道是谁 |

所以硬规矩：

> **浏览器永远只和后端说话，数据库永远不暴露到公网。**

我们现在的结构就是这条规矩的落地：`sentinel.db` 是本地文件，
`demo.py` 是唯一能碰它的进程，浏览器只能通过 `/api/*` 间接操作。

## 五、几个容易被忽略的细节

### 1. 每个请求一个新连接

`db.py` 的 `connect()` 每次都重新打开连接，请求结束就关。

```python
def connect():
    conn = sqlite3.connect(DB_PATH)
    conn.row_factory = sqlite3.Row
    return conn
```

简单、不会串数据；代价是并发高了要换连接池。

### 2. 参数化查询，不拼字符串

```python
conn.execute("UPDATE review_queue SET status=? WHERE id=?", (status, rid))   # 对
conn.execute("UPDATE review_queue SET status='%s' WHERE id=%s" % (...))      # 错
```

第一种写法里，`?` 是占位符，SQLite 会把参数当**值**处理；
第二种写法如果参数里带 `'; DROP TABLE ...` 就会被当 SQL 执行。**注入漏洞就是这么来的。**

### 3. 写完之后前端要重新拉数据

我们每次写完都调用 `loadQueue()` / `loadMetrics()` 重新 `GET` 一次。
没有做「前端本地改状态」，因为那样一旦后端写失败，界面就和数据库不一致了。

**原则：数据库是唯一事实来源，界面永远从它读。**

### 4. 只读模式是怎么拦住的

部署到公网时设 `READONLY=1`，`do_POST` 一进来就返回 403：

```python
def do_POST(self):
    if READONLY:
        return self._send(403, {"error": "演示环境为只读"})
```

**拦截在后端**，不是靠前端把按钮藏起来——前端藏按钮只挡君子。

## 六、自己验证的三个办法

**办法 1：看接口返回**
点一下按钮，F12 → Network → 看那个 POST 的 Response，里面有 `review_id` 或 `case_no`。

**办法 2：看数据库行数**
操作前后各跑一次：

```python
import sqlite3
c = sqlite3.connect("demo/sentinel.db")
print(c.execute("SELECT COUNT(*) FROM review_queue").fetchone())
```

**办法 3：DBeaver 里刷新**
打开 `review_queue` 表，点刷新，新那行就在最底下（按 id 倒序看最上面）。

## 七、一张表看清「谁写谁」

| 数据 | 谁写 | 写进哪 | 触发时机 |
|---|---|---|---|
| 判定流水 | 后端自动 | `judge_logs` | 每次调用 `/api/judge` 或批量跑 |
| 待复核 | 后端自动 | `review_queue` | 判定不了时 |
| 裁决结果 | 后端（人工触发） | `review_queue.status` | 审核管理点按钮 |
| 介入单 | 后端（人工触发） | `cases` | 裁决=确认介入 |
| 通知 | 后端（人工触发） | `notifications` | 同上 |
| 商家违规 | 后端（人工触发） | `merchants.violations` | 同上 |
| 规则候选 | 后端（人工触发） | `rule_candidates` | 任何一次裁决 |

**没有任何一行是前端直接写进数据库的**——全部经过后端。
