# 召回与缓存：已有答案怎么复用

核心问题：**同一句话（或换了个说法的同一句话）第二次出现时，能不能不重新判定？**

能。判定链路上加了一层召回，命中就跳过规则和模型，**成本 0、耗时 < 1ms**。

---

## 一、判定链路变成四段

```
归一化
  ├─ ① 精确召回   key = sha1(归一化文本)        O(1)
  ├─ ② 相似召回   SimHash 分桶 → Dice 精排
  ├─ ③ 规则判定   命中即定案
  └─ ④ 模型判定   小模型 → 大模型 → 人工
                              ↓
                        写回缓存（只存敢复用的）
```

①②命中 → 直接返回缓存结论，`cached` 字段标明 `exact` 或 `fuzzy`。

---

## 二、精确召回：为什么先归一化

```python
normalize("您好，好评返现５元！！") → "您好好评返现5元"
key = sha1(normalize(text))[:16]
```

归一化做了三件事：
1. **NFKC** —— 全角 `５` → 半角 `5`，全角标点 → 半角
2. **去标点与空白** —— `\W` 全部剔除
3. **转小写**

于是这些都会被认成同一条：

| 原句 | 归一化后 |
|---|---|
| 特价商品不退不换 | 特价商品不退不换 |
| 特价商品不退不换！！！ | 特价商品不退不换 |
| 特价商品，不退不换 | 特价商品不退不换 |

**为什么不用原始文本做 key**：标点、空格、全半角的差异是噪声，不是语义。用原文做 key，命中率会低一个数量级。

---

## 三、相似召回：SimHash + Dice 两道闸

光有精确召回不够——**"换了说法"才是大头**（留出集里换了说法的命中率是 0%）。

### 第 1 步：SimHash 分桶（粗筛）

```python
bigrams("可以给你退你先把差评删了")
→ {"可以","以给","给你","你退","退你",...}

simhash = 64 位：每个 bigram 取哈希，按位投票（1 加、0 减），> 0 置 1
bands   = 切成 4 段 × 16 位 → ["0:12345","1:6789",...]
```

分桶存进 `cache_band`，查询时用 `band IN (...)` 取候选。
**作用是不相似的句子直接不进候选**，避免全表比。

### 第 2 步：Dice 精排（细筛）

```python
dice(A, B) = 2|A∩B| / (|A|+|B|)     # A、B 是 bigram 集合
```

取候选里 Dice 最高的一条。

### 第 3 步：两道闸决定认不认

| Dice | 判断 | 理由 |
|---|---|---|
| ≥ 0.62 | **直接认** | 近似重复，措辞几乎一样 |
| 0.28 ~ 0.62 | 要求**缓存的命中词出现在新句里**，才认 | 中等相似容易误召回，用触发词做锚 |
| < 0.28 | 不认 | 视为新问题 |

**阈值的来源是实测，不是拍的**：

| 关系 | 实测 Dice |
|---|---|
| 同义改写（可以退，你先把差评删掉 / 原句） | 0.70 |
| 同义改写（你先删差评，我再给你退款 / 原句） | 0.38 |
| 同义改写（你加我微信，直接转给我 / 加我微信转账给你） | 0.38 |
| 不同意图（好评返现5元 / 原句） | 0.00 |
| 不同意图（特价商品不退不换 / 原句） | 0.00 |

同义 0.30~0.70，异义 0.00 —— 中间有很宽的空档，所以 0.28/0.62 这两条线是安全的。

### 为什么要"命中词"这道闸

看这条真实数据：

```
缓存句：可以给你退，你先把差评删了   （命中词：差评删）
新句子：你先删差评，我再给你退款
Dice = 0.38
```

Dice 够 0.28，但命中词 `差评删` 不在新句里 → **不认**。
这是**故意的保守**：0.38 的相似度可能是"同一类问题"，也可能是"完全不同的两件事"，加一个词面锚点能挡掉大部分误召回。

## 四、数据结构

```sql
decision_cache(
  id, key,              -- 精确召回
  text, norm,           -- 原文 / 归一化文本
  simhash,              -- 64 位，存为有符号整数
  verdict,              -- 整个判定结果的 JSON
  source,               -- rule / human / small / large
  conf,                 -- 置信度
  rule_ver,             -- 规则库版本
  hits, ts, last_hit    -- 命中次数与时间
)

cache_band(band, cache_id)   -- LSH 桶，band 上有索引
```

`verdict` 存的是**完整返回体**（rule / llm / tier / pending_review），
所以命中时能原样返回，包括条款依据和提醒卡文案。

## 五、什么敢缓存，什么不敢

| 情况 | 存不存 | 理由 |
|---|---|---|
| 规则直接定案（tier=rule） | ✅ conf 0.95 | 确定性判定，规则一改就靠 `rule_ver` 失效 |
| 人工裁决过（approve/reject） | ✅ | 人给的结论最可信 |
| 模型判定且置信 ≥ 0.8 | ✅ conf 取模型置信 | 高置信才敢复用 |
| 模型置信 < 0.8 | ❌ | 复用低置信结论 = 放大错误 |
| **进了待复核队列** | ❌ **绝不** | 没结论的东西不能缓存 |

最后一条是红线：**缓存的是结论，不是过程**。一条 `pending_review` 的样本没有结论，缓存它等于假装它被处理过了。

## 六、失效与一致性

缓存最大的风险是**过期**。三个机制：

### 1. 规则版本号

```python
rule_version() = sha1(rules.jsonl 文件内容)[:10]
```

缓存行记下当时的 `rule_ver`，查询时比对。**规则库一改，所有旧缓存自动失效**（不删，但不再命中）。

这意味着：改完规则重启服务，缓存命中率会掉到 0，然后慢慢重建。这是正确的行为。

### 2. 人工裁决清缓存

```python
decide_review(...) → cache_drop(row["text"])
```

`cache_drop` 会删掉**这句话本身**和**与它相似的所有条目**（Dice ≥ 0.28）。
因为人工推翻了机器结论，说明这类判断不可靠。

### 3. 手动清空

```bash
curl -X POST http://127.0.0.1:8765/api/cache/clear
```

## 七、实测效果

40 次调用（20 条话术，每条判 2 次）：

```
命中 19 次，命中率 48%
缓存 17 条可用 · 已复用 23 次
成本 0.00
```

单条判定路径对比：

| 路径 | 耗时 | 成本 |
|---|---|---|
| 缓存命中 | < 1ms | 0 |
| 规则判定 | < 1ms | 0 |
| 小模型 | 300–1000ms | 1 单位 |
| 大模型 | 2–5s | 10 单位 |

**缓存的价值不只是快，是省掉模型调用**——而模型调用正是三层里唯一花钱的部分。

真实客服场景里重复率很高（"我要退货""多少钱""什么时候到"能占一半以上），
命中率通常能到 **40%~70%**。

## 八、局限（必须知道）

### 1. 词面相似 ≠ 语义相似

| 两句 | Dice | 实际关系 |
|---|---|---|
| 好评返现5元 / 五星返钱 | 0.00 | **同一个意思**，但召不到 |
| 可以退，先删差评 / 可以退，先删评论 | 0.70 | 意思接近，且都是"以利益换好评" |

字符 bigram 抓不住"换了词但意思一样"的情况。**这是当前方案最大的短板，也是留出集里"换了说法 0% 命中"的同一个病根**。

### 2. 误召回会放大错误

一条判错的缓存，会被复用到所有近似句上。
三道防线：只缓存高置信、规则版本号失效、人工裁决即清。

### 3. 缓存不稳定会掩盖问题

如果命中率突然从 50% 掉到 10%，可能是规则改过导致全部失效——**这不是 bug，但需要监控**，否则会误判为"系统变差了"。

## 九、怎么升级成向量召回

当前接口已经留好了，换两个函数即可：

| 现在 | 换成 |
|---|---|
| `recall.bigrams` + `dice` | embedding（如 qwen text-embedding） + cosine |
| `cache_band` LSH 分桶 | 向量索引（FAISS / HNSW / pgvector） |

`db.cache_similar` 的签名不用变，只是把"候选召回 + 打分"内部换掉。

**收益**：能召回"好评返现 / 五星返钱"这类同义不同词的句子，命中率预计再涨 15~25 个百分点。
**代价**：每次查询要调一次 embedding（几毫秒），且需要向量库。

**建议**：先用字符相似跑起来，把命中率基线测出来（现在 48%），再决定要不要为提升那 15 个点引入向量检索。

## 十、观测指标

```bash
curl http://127.0.0.1:8765/api/cache/stats
```

```json
{"total": 17, "live": 17, "stale": 0,
 "saved_calls": 23, "rule_ver": "4e42f12448",
 "by_source": [{"source": "rule", "n": 17, "h": 23}]}
```

| 字段 | 含义 | 异常信号 |
|---|---|---|
| `total` / `live` | 总数 / 当前规则版本可用的数量 | `stale` 暴涨 = 刚改过规则 |
| `saved_calls` | 累计复用次数 | 长期不涨 = 命中率太低 |
| `by_source` | 各来源的缓存条数与命中 | `human` 占比过高 = 说明模型判不了 |

自主输入页的「累计统计」里也实时显示：

> 缓存：17 条可用 · 已复用 **23** 次

## 一句话总结

> **精确召回解决"同一句"，相似召回解决"换个说法"，规则解决"确定的"，模型解决"没见过但能推的"。**
> 缓存不是加速器，是**成本的闸门**——它决定了你有多少次判定根本不需要花钱。
