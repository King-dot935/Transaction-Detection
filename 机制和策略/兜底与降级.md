# 兜底与降级

降级的目标不是“还能返回一个结果”，而是：依赖故障时，系统行为仍然可预测、可解释、可审计，并优先选择更保守的处理方式。

## 1. 设计原则

1. **只降不升**：外部依赖故障不能把“不确定”变成“自动放行”。
2. **降级留痕**：模型、缓存和事件写入失败都记录 `degrade_events`。
3. **熔断优先**：连续失败后停止打上游，避免故障时产生重试风暴。
4. **预算优先**：单条判定总耗时受 `BUDGET_MS` 限制，模型请求本身也使用剩余预算。
5. **恢复有界**：熔断器进入半开状态时只允许一个探测请求通过。

## 2. 当前链路

```text
输入安全检查
  → PII 脱敏与归一
  → 缓存查询（有独立熔断）
  → 规则判定
  → 小模型（可选）
  → 大模型（可选）
  → 人工复核
  → 规则/条款结论 + 处置动作
```

模型调用由 `resilience.call_model()` 统一包装，负责：

- 检查熔断状态。
- 检查剩余时间预算。
- 将超时、无返回、解析失败计为失败。
- 成功时关闭熔断器，失败时累计失败次数。

## 3. 故障处理矩阵

| 依赖 | 故障表现 | 当前行为 | 用户结果 |
|---|---|---|---|
| 小模型 | 超时、401、解析失败 | 熔断；回落规则 | 规则确定则继续，否则转人工 |
| 大模型 | 超时、401、解析失败 | 放弃升级，保留已有结论 | 不确定则转人工 |
| 两层模型 | 都熔断 | `safe` 模式 | 只走规则与人工 |
| 缓存 | 查询或写入异常 | 缓存熔断并跳过 | 变慢，不改变规则结论 |
| 事件库 | 埋点写入异常 | 记录降级日志，不影响判定响应 | 主流程继续 |
| 规则文件 | 缺失或损坏 | 启动阶段失败 | 服务不启动，避免带病运行 |
| SQLite 写入 | 锁冲突、磁盘满 | 请求失败并暴露明确错误 | 当前没有自动只读切换 |
| 人工队列 | 积压超过软阈值 | 不确定样本仍转人工并提示延迟 | 待复核量继续受控 |
| 人工队列 | 积压超过硬阈值 | 停止新判定并返回 `skipped=shed` | HTTP 503，提示稍后重试 |
| 安全输入 | 提示注入/控制字符 | 跳过模型和缓存 | 强制人工复核 |

## 4. 熔断状态机

```text
closed
  └─ 窗口内失败达到 3 次 → open
open
  └─ 等待 30 秒 → half_open
half_open
  ├─ 唯一探测成功 → closed
  └─ 探测失败 → open，重新计时
```

半开状态有单探测锁，避免上游刚恢复时同时涌入大量请求。缓存和两层模型分别维护独立熔断器。

## 5. 时间预算

默认 `BUDGET_MS=2500`。预算不仅用于决定“还要不要调模型”，也传给 `llm.judge()` 作为 HTTP timeout 的上限。

```python
budget = resilience.Budget(BUDGET_MS)
model, elapsed = resilience.call_model(
    tier,
    lambda: llm.judge(text, tier, timeout=budget.slice(BUDGET_MS)),
    budget,
)
```

这修复了此前“外层预算 2.5 秒，但 HTTP 请求仍可等待 40 秒”的不一致。

## 6. 状态与演练

查看状态：

```powershell
curl.exe http://127.0.0.1:8765/api/system/status
```

返回内容包含：

- 当前模式：`normal` / `degraded` / `safe`
- 每个熔断器的状态和窗口内失败数
- 时间预算
- 最近降级事件和安全事件
- 当前待复核数量与背压等级

纯熔断器演练：

```powershell
python drill_resilience.py
```

演练覆盖：

- 连续三次失败进入 `open`
- `open` 期间拒绝请求
- 等待后进入 `half_open`
- 单次探测成功恢复 `closed`
- 半开探测失败重新进入 `open`

## 7. 当前不足

| 缺口 | 影响 | 下一步 |
|---|---|---|
| SQLite 是单点 | 文件损坏或磁盘满时无法继续写 | 定时备份、损坏检测、只读降级 |
| 熔断/限流状态只在进程内 | 多实例配额和状态不一致 | 迁移到 Redis 或网关 |
| 没有重试队列 | 模型恢复后，历史不确定样本不会自动重判 | 增加 durable queue 与幂等消费者 |
| 降级只写表 | 值班人员不会即时收到通知 | 接告警平台和 SLO 告警 |
| 没有缓存预热 | 冷启动时规则压力更大 | 按规则版本预计算高频样本 |
| 无可观测 trace 导出 | 排障仍依赖单机数据库 | 接入 OpenTelemetry 或集中日志 |

## 8. 验证标准

最小验收不是“模型错误时服务不崩”，而是：

1. 高风险规则命中仍然产生结果。
2. 规则不确定且模型不可用时进入人工队列。
3. 注入文本不调用模型、不写缓存。
4. 模型失败不会让单条请求无限等待。
5. 半开恢复只产生一个探测请求。
6. 每次降级都有可检索记录。

当前代码满足以上行为，但“数据库故障自动切只读”“模型恢复后自动重判”仍然没有实现，不能写成已完成。
