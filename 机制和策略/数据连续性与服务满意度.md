# 数据连续性 & 服务满意度：怎么保证、怎么验证

两个问题本质上是一件事的**两个时间尺度**：
数据连续性看"过去的数据还在不在"，服务满意度看"此刻的请求好不好"。

---

# 第一部分：数据连续性

## 一、"不丢数据"要先定义清楚

| 数据 | 能不能丢 | 现在怎么保证 |
|---|---|---|
| 已提交的判定记录（`judge_logs`） | **不能丢** | 单事务写入 + WAL + `synchronous=NORMAL` |
| 待复核样本（`review_queue`） | **不能丢** | 同上 |
| 介入单（`cases`） | **不能丢** | 同上 |
| 缓存（`decision_cache`） | 可丢 | 丢了只是重新判一次 |
| 熔断/限流状态 | 可丢 | 进程内，重启清零 |
| 降级/安全事件 | 尽量不丢 | 同事务写库 |

**关键判断**：缓存和熔断状态可以丢，业务结论不能丢。这决定了加固的重点在哪。

## 二、四层保证

### 第 1 层：事务边界

所有写操作都在 `with conn:` 里，一次事务要么全成要么全不成：

```python
with conn:
    conn.execute("UPDATE review_queue SET status=? ...")
    cache_drop(row["text"])
```

**没有跨事务的"半步写入"**——比如裁决时"改了队列但没生成介入单"这种情况不会发生。

### 第 2 层：WAL + 同步级别

```python
conn.execute("PRAGMA journal_mode=WAL")     # 崩溃可恢复
conn.execute("PRAGMA synchronous=NORMAL")   # 已提交事务不丢
conn.execute("PRAGMA busy_timeout=5000")    # 抢锁最多等 5 秒
```

| 参数 | 作用 | 代价 |
|---|---|---|
| WAL | 写不阻塞读；崩溃后自动回放 | 多两个 `-wal`/`-shm` 文件 |
| `synchronous=NORMAL` | 崩溃只可能丢"最后一个事务"，已提交的不丢 | 比 FULL 快很多 |
| `busy_timeout` | 并发写时不立刻报 database is locked | 极端情况下最多等 5 秒 |

**为什么不用 FULL**：FULL 每次提交都 fsync，写入速度掉一个数量级；
这个系统丢一个事务的代价远小于吞吐掉 10 倍。

### 第 3 层：备份

```bash
python backup.py            # 备份 + 校验 + 清理
python backup.py --check    # 只做完整性检查
python backup.py --list     # 看历史备份
```

用 **SQLite 官方 backup API**，不是 `cp`：

| 方式 | 一致性 | 会不会锁库 |
|---|---|---|
| `cp sentinel.db` | ❌ 可能拷到写一半的状态 | 可能 |
| `sqlite3 .backup` / Python `backup()` | ✅ 一致性快照 | 不锁 |

保留最近 **7 份**，自动清理。实测：

```
备份完成：sentinel-20261110-215802.db（184 KB）· 完整性 ok（judge_logs 322 行）
```

### 第 4 层：校验

```bash
python backup.py --check
# 通过：ok（judge_logs 322 行）
```

`PRAGMA integrity_check` 会扫全库结构和索引。**备份完立刻校验**，避免"备份了一个坏文件还以为安全"。

## 三、崩溃恢复实测

用 `Stop-Process -Force` 强杀进程（模拟断电，不给优雅退出）：

| 表 | 崩溃前 | 恢复后 |
|---|---:|---:|
| judge_logs | 322 | **322** |
| review_queue | 54 | **54** |
| cases | 19 | **19** |
| decision_cache | 12 | **12** |

```
最后一条记录 id=322（时间戳一致）
PRAGMA integrity_check: ok
```

**结论：已提交数据零丢失。**

## 四、RPO / RTO

| 指标 | 值 | 依据 |
|---|---|---|
| RPO（最多丢多少数据） | **≈ 0 个已提交事务** | WAL + 单事务写入 |
| RTO（多久能恢复） | **分钟级** | 重启进程即恢复；极端情况从备份还原 |
| 备份保留 | 7 份 | 约一周的回滚窗口 |

## 五、审计连续性（这个更重要）

数据不丢只是一半，另一半是**"谁在什么时候改了什么"**不能丢。

| 表 | 记录什么 | 能不能改 |
|---|---|---|
| `judge_logs` | 每次判定（含规则、模型、分流、耗时） | 只增不改 |
| `review_queue` | 裁决人、理由、时间 | 改状态但保留原因 |
| `cases` | 介入单与处置证据 | 只增 |
| `degrade_events` | 每次降级 | 只增 |
| `security_events` | 注入/限流/大包 | 只增 |

**审计的价值在于"事后能还原现场"**：一条判定被推翻时，能看到当时的规则版本、模型置信、人工理由。

# 第二部分：服务满意度

## 一、先定义"满意"是什么

技术指标不等于用户满意。三层：

| 层 | 指标 | 现在有吗 |
|---|---|---|
| 技术层 | 延迟、错误率、可用性 | ✅ SLO 已实现 |
| 行为层 | 点击率、跳过率、误报反馈 | ⚠️ 只有误报，缺点击/跳过 |
| 认知层 | 用户是否相信这个提醒、是否真的拿它去维权 | ❌ 完全没有 |

## 二、SLO 六项（已实现）

```bash
curl http://127.0.0.1:8765/api/slo
```

| 指标 | 当前 | 目标 | 状态 |
|---|---|---|---|
| 判定延迟 P95 | **42 ms** | ≤ 800 ms | ✅ |
| 待复核率 | **10%** | ≤ 15% | ✅ |
| 满意度（反馈正面率） | **0%**（1 条反馈） | ≥ 80% | ❌ |
| 数据新鲜度 | 0.3 分钟前 | ≤ 5 分钟 | ✅ |
| 数据库完整性 | 正常 | integrity_check ok | ✅ |
| 最近备份 | 0.0 小时前 | ≤ 24 小时 | ✅ |

**通过 5/6**，唯一不过的是满意度——但**这不是失败，是样本不足**：
只有 1 条反馈，且是误报。1 条数据算出来的比例没有意义。

**这个 SLO 的价值不是"打分"，是强迫你面对三个问题**：
1. 延迟目标定得合理吗（800ms 是否太松）
2. 待复核率 10% 是常态还是异常
3. 满意度没数据，说明反馈入口没人用

## 三、为什么"满意度"现在不可用

| 问题 | 现状 |
|---|---|
| 反馈入口太深 | 只有提醒卡上的「准/误报」两个按钮 |
| 样本量 | 1 条 |
| 缺少负向信号 | 没有"跳过""关掉提醒"的埋点 |
| 没有时效感知 | 用户不知道"多久会有人处理" |

**只有"准/误报"这一种反馈是不够的**——它测的是"判得对不对"，
测不到"这个产品对我有没有用"。

## 四、要补的三类满意度信号

| 信号 | 怎么采 | 说明什么 |
|---|---|---|
| 提醒卡点击率 | 点"申请平台介入"的比例 | 提醒是否被认可 |
| 跳过/关闭率 | 关掉提醒的比例 | 是否打扰 |
| 介入单后续 | 介入单最终是否退款成功 | 真正的价值 |

**第三个最关键，但现在完全没有**：用户点了"申请介入"，然后呢？
如果没有闭环（退款了没有、多久退的），前面的指标再好看都是自嗨。

## 五、满意度不能只看平均值

| 陷阱 | 说明 |
|---|---|
| 平均值掩盖长尾 | P95 延迟 42ms，但如果 5% 的用户等了 5 秒，他们才是流失的那批 |
| 幸存者偏差 | 只有愿意点反馈的人会点，不满的人直接走了 |
| 样本太小 | 1 条反馈算出的 0% 毫无意义 |
| 没有对照组 | 不知道"不提醒"会不会更好 |

**这也是为什么我把「数据新鲜度」「备份年龄」放进 SLO**——
它们在技术上和"满意度"无关，但**服务烂掉之前，这些指标一定先异常**。

---

## 六、缺口与下一步

| 顺序 | 动作 | 为什么 |
|---:|---|---|
| 1 | 前端埋点：点击/跳过/关闭 | 没有行为数据，满意度无法度量 |
| 2 | 介入单闭环追踪（退款是否到账） | 这是产品真正的价值验证 |
| 3 | 定时备份（每天一次）+ 备份失败告警 | 现在是手动跑，容易忘 |
| 4 | 反馈样本 ≥ 30 条再启用满意度判定 | 现在 1 条没有统计意义 |
| 5 | 加"响应时效承诺"（如 24h 内处理） | 用户最关心的是"多久有结果" |

## 七、一句话总结

> **数据连续性靠"事务 + WAL + 备份 + 校验"四层，实测强杀进程零丢失。**
> **服务满意度靠"技术 SLO + 行为埋点 + 业务闭环"三层，现在只做到第一层。**
> 而满意度真正的证据不在按钮上，在**用户点完介入之后，钱有没有退回来**。
