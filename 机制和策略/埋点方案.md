# 埋点与可观测性

当前实现覆盖了演示环境内的“判定 → 曝光 → 点击 → 人工裁决”链路，但没有接入真实 IM、支付或工单系统，因此不能计算退款成功率、二次投诉率等业务结果指标。

## 1. 当前链路

```text
商家文本
  → judge_result（服务端）
  → card_exposure（提醒卡渲染）
  → card_evidence_open / card_click_intervene
  → card_feedback
  → review_open（进入审核管理）
  → case_decide（提交人工裁决）
```

所有事件使用同一个 `trace_id` 串联。服务端判定先产生 `judge-*` 或 `session-*` 形式的 ID；前端提交事件时必须回传该 ID。

## 2. 事件字典

| 事件 | 产生方 | 必填属性 | 说明 |
|---|---|---|---|
| `judge_result` | 服务端 | tier、hit、lat_ms、cost_units | 每次自动判定 |
| `card_exposure` | 页面 | rule_id、type、severity、position | 提醒卡实际渲染 |
| `card_evidence_open` | 页面 | action | 展开证据快照 |
| `card_click_intervene` | 页面 | action | 点击申请平台介入 |
| `card_feedback` | 页面/服务端 | useful、rule_id | 准/误报反馈 |
| `review_open` | 审核页 | pending | 进入审核管理 |
| `case_decide` | 服务端 | action、preset、rule_hit | 人工裁决完成 |

事件格式：

```json
{
  "event": "card_click_intervene",
  "schema_version": 1,
  "trace_id": "judge-1f0d33d7c328",
  "session_id": "S03",
  "properties": {
    "rule_id": "R03",
    "action": "open_ticket"
  }
}
```

## 3. 写入与查询

事件表：

```sql
events(
  id, ts, event, schema_ver, trace_id,
  session_id, actor_id, properties
)
```

查询：

```powershell
curl.exe http://127.0.0.1:8765/api/events/stats
```

接口返回：

- 事件总量和按事件类型的计数。
- 唯一 `trace_id` 数量。
- 介入点击率、证据查看率、反馈率。
- 曝光样本不足 30 时的提示。

指标公式：

```text
介入点击率 = card_click_intervene / card_exposure
证据查看率 = card_evidence_open / card_exposure
反馈率 = card_feedback / card_exposure
```

当前接口只做链路完整性验证。曝光样本不足时返回 `None`，不以 0% 冒充“用户不点击”。

## 4. 为什么这样设计

| 设计 | 原因 |
|---|---|
| 曝光和点击分开 | 点击率必须有正确分母 |
| 固化 `trace_id` | 把判定、提醒、反馈、人工裁决串起来 |
| 事件白名单 | 防止客户端随意写入未治理事件 |
| 属性 4 KiB 上限并脱敏 | 控制存储成本和敏感信息风险 |
| 事件写入失败不阻断判定 | 可观测性不能成为主链路单点 |
| 区分服务端与客户端事件 | 服务端判定是事实，客户端行为是体验信号 |

## 5. 当前无法判断的问题

| 问题 | 缺少的数据 |
|---|---|
| 提醒卡有多少用户真的看到？ | 当前只有自建页面曝光，没有真实客户端和可见性校验 |
| 申请介入后是否退款到账？ | 缺少订单、支付、工单回调 |
| 是否发生二次投诉？ | 缺少投诉系统数据 |
| 哪类用户更容易采纳提醒？ | 没有真实账号、分群和授权 |
| 拦截后商家是否改写话术？ | 没有商家输入端埋点 |

因此当前不能宣称“产品提升了退款率”或“降低投诉率”。能证明的只是演示链路事件已能被采集、脱敏和按 `trace_id` 聚合。

## 6. 生产化方案

### 6.1 接入

- 客户端使用统一 SDK 或事件总线，失败本地缓存并批量上报。
- 服务端判定、人工裁决直接写事件表。
- 客户端与服务端双写，以 `trace_id + event` 去重。
- 通过订单号和会话号关联下游退款、投诉和工单状态。

### 6.2 治理

- 每个事件必须有负责人、版本、触发时机和下线计划。
- 枚举值收敛，属性不允许无限自由文本。
- 高频事件采样要明确采样率，并保留可还原总分母的方法。
- 客户端事件延迟到达时，保留归因窗口。
- 对曝光、点击、裁决设置对账任务：客户端曝光不应显著大于服务端判定。

### 6.3 合规

- 聊天原文属于敏感业务数据，应按最小必要原则采集。
- 事件属性只放分类和 ID，不默认携带完整会话。
- 设置留存期限、删除机制和访问审计。
- 用户撤回授权后，离线链路与备份也要有清理策略。

## 7. 结论边界

当前实现覆盖服务端判定事件、提醒卡曝光、点击、证据查看、反馈和人工裁决，并用 `trace_id` 串联链路。由于没有真实支付和投诉回调，现阶段只能验证行为链路和统计口径，不能据此计算退款转化率、GMV 或投诉下降。

上述业务结论需要真实数据源、身份体系、下游结果和对照实验，超出当前原型范围。
