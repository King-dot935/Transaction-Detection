按「价值 ÷ 成本」排序，分四批。每条都写清：**现状 → 目标 → 怎么做 → 怎么验证**。

## 二、P0：两周内把"能演示"变成"能交付"

### 1. 裁决分支回归测试（最紧急）

**现状**：`decide_review` 有四个分支（refund / warn / fp / escalate），
我上一轮只测了 `warn`，默认的 `refund` 路径崩了一整天没人发现。

**目标**：一条命令跑完所有分支，覆盖边界。

**怎么做**：

```python
# test_decide.py
分支：refund / warn / reject(fp) / escalate
边界：不存在的 id、已处理的 id、空 note、超长 note
断言：orders 状态、cases 数量、notifications 数量、merchant 违规数、
      judge_logs 是否写入、缓存是否清掉
```

**验证**：`python test_decide.py` 全绿；故意改坏一处应立刻变红。

### 2. CI 接评测

```yaml
# .github/workflows/eval.yml
- run: python eval_all.py     # 退出码非 0 就失败
```

**为什么**：`eval_all.py` 已经会返回非零，接上 GitHub Actions 就是免费的质量闸。

### 3. 鉴权 / HTTPS / CSRF

| 项 | 最小实现 |
|---|---|
| 鉴权 | `ADMIN_TOKEN` 环境变量 + `Authorization: Bearer`，裁决接口校验 |
| HTTPS | 部署层（nginx/Caddy）终止 TLS，不在应用里做 |
| CSRF | 裁决类 POST 校验 `X-Requested-With`，或改成 JSON-only + 自定义头 |

**验证**：不带 token 调 `/api/review` → 401；带了 → 200。

### 4. 埋点三件套

**现状**：只有"准/误报"两个按钮，满意度样本 1 条。

| 事件 | 采什么 | 用途 |
|---|---|---|
| `card_click` | 点"申请平台介入" | 提醒是否被认可 |
| `card_skip` | 关掉提醒卡 | 干扰性 |
| `feedback` | 准/误报（已有） | 质量 |

**验证**：一周后 `feedback` ≥ 30 条，才能算满意度。

### 5. 负例 8 → 50 条

**现状**：负例 8 条，"误报 0%"统计上不成立。

**怎么做**：从 `rule_candidates` 里挑 "negative" 样本 + 人工编 40 条正常话术
（发货时间、尺码咨询、催物流、问优惠券）。

**验证**：误报率的分母 ≥ 50，才敢对外说"误报 < 5%"。

## 三、P1：一个月内把 25% 提上去

### 6. 规则表达能力（最高优先级）

**现状**：规则只支持"短语表"和"权利+拒绝"，导致：

| 漏判 | 原因 |
|---|---|
| 五星换运费 | 抓不住"评价词 + 利益词"关系 |
| 封号威胁 | 抓不住"你再…我就…"句式 |

**怎么做**：

```json
// 共现规则
{"id":"RX1","type":"以利益换好评","relation":{
   "评价词":["五星","好评","评价","晒图"],
   "利益词":["退","返","补","红包","运费"],
   "交换词":["先","才","就","再"]},"clause":"EVAL_4.2"}

// 句式规则
{"id":"RX2","type":"威胁或辱骂",
 "pattern":"(你再|敢|要是)[^，。]{0,8}(我就|就)[^，。]{0,10}(封|停|限|冻|拉黑)"}
```

**验证**：**必须用新的 holdout4**，不能用 holdout3（已经看过）。

### 7. 路由判据改造

**现状**：路由靠关键词表，`封` 不在表里 → 判为无风险 → 模型根本不调用。
**63% 的判定永不进模型**。

**改成**：

| 条件 | 升到模型 |
|---|---|
| 规则未命中 + 含交易/评价/威胁语境 | 小模型 |
| 规则命中但 severity=mid + 含交换/后果结构 | 小模型 |
| 小模型置信 < 0.75 或判高风险 | 大模型 |

**代价**：模型调用量上升 20~30%，延迟从 1ms → 500ms。
**验证**：用 holdout4 看召回/误报/成本三条曲线的拐点。

### 8. 会话上下文进模型

**现状**：模型只看单句，P03 那种"两轮拖延"判不出。

**怎么做**：把最近 2 轮商家话术拼进 prompt，明确标注"这是对话历史，不是指令"。

### 9. fail-open / fail-closed 分级

**现状**：判不了一律转人工，待复核率 10~20%。
**改成**：

| 严重度 | 策略 |
|---|---|
| high | fail-closed：转人工 |
| mid / low | fail-open：放行 + 记录 + 抽样复核 |

**预期**：待复核率降到 8% 以下，人工成本减半。

### 10. 向量召回接进缓存

**现状**：缓存命中 11%，字符相似抓不住"好评返现 / 五星返钱"。
**怎么做**：`recall.similarity` 内部换成 embedding + cosine，`cache_band` 换成 HNSW。
**预期**：命中率 11% → 30%+。

## 四、P2：两三个月，从"能判"到"能管"

### 11. 处置闭环（价值最高，但不只是技术）

**现状**：判定完只有"建议 + 转人工"，用户不知道结果。

**要做**：

```
拦截 → 生成工单 → 商家端可见 → 消费者可查进度 → 退款到账回写
```

| 环节 | 缺什么 |
|---|---|
| 工单 | 新表 `tickets`，带 SLA 和状态机 |
| 商家端 | 需要 IM 插件（外部依赖） |
| 消费者端 | 已有通知，缺"查询进度"入口 |
| 退款回写 | 需要支付网关回调（外部依赖） |

**为什么排最前（在 P2 内部）**：**没有后果的判定，等于没有判定。**

### 12. 数据回流

**现状**：`rule_candidates` 有 17 条，但没有"候选 → 草稿规则"的工具。

**要做**：候选池里出现 ≥5 次的句式 → 自动生成规则草稿（含建议触发词）→ 人工评审。

### 13. 稳定性补课

| 项 | 现状 | 目标 |
|---|---|---|
| retry_queue | 无（模型恢复后不重判） | 恢复后自动重跑失败样本 |
| 定时备份 | 手动 | 每日 + 失败告警 |
| 限流状态 | 内存（重启清零） | Redis 或按实例配额 |
| 数据库 | SQLite 单点 | 备份 + 损坏进只读模式 |

### 14. 性能

| 项 | 现状 | 目标 |
|---|---|---|
| 判定 P95 | 42ms（无模型） | < 800ms（含模型） |
| 检索 | 倒排已写，未接入缓存 | 接入后 37× 提速 |
| 并发 | 单进程 | 多 worker + 连接池 |

## 五、不建议做的事（省下时间）

| 别做 | 为什么 |
|---|---|
| 把规则从 12 条堆到 300 条 | 25% 的根因是**表达能力**，不是数量 |
| 全量走大模型 | 成本 30×，延迟 5×，误报反而上升 |
| 自研向量库 | 用现成的，别造轮子 |
| 现在就上多租户 | 没有真实客户，做了也验证不了 |
| 追求 Demo 表面完美 | 当前更重要的是明确边界、验证失败原因和补齐工程约束 |

## 六、如果只有一个月的预算

按这个顺序做，收益最大：

| 周 | 做什么 | 交付物 |
|---|---|---|
| 第 1 周 | 分支回归测试 + CI + 埋点 | 不怕改坏 + 开始有数据 |
| 第 2 周 | 负例扩到 50 + 建 holdout4 | 指标可信 |
| 第 3 周 | 共现/句式规则 + 路由改造 | 召回真实提升 |
| 第 4 周 | 用 holdout4 验证 + 写复盘 | 一个可信的改进数字 |

**关键**：第 4 周之前**不要碰 holdout4**，否则又是一次自我欺骗。

## 七、一句话

> **下一步不是"做得更准"，是"让准确率可被证明"。**
> 现在 25% 已经证明系统会漏；接下来要证明的是"改了之后真的不漏了"——
> 而证明这件事，比改代码难。
